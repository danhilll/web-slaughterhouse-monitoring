## 2. Blocking stakeholder decisions

- **Measurement:** approve the dressed-carcass body-part inclusion/exclusion definition. Existing design already agrees on grams, writers, timing and corrections; no yield or weight-ratio rule is proposed. Carcass remains separate from live weight and does not silently change invoice eligibility or fees.
- **Fees:** provide the approved component amounts, charge basis, effective date and authority/reference. Current four components and per-animal basis are implementation constraints, not an official tariff. Do not copy demo schedules into production.
- **Numbering:** approve invoice/receipt format, sequence scope/reset rules, issuance responsibility and handling of retries/gaps/voids. Keep the deterministic `AINV-...` ID as an internal duplicate-prevention key; it is not an approved official invoice number. Add transactionally reserved official-number fields and show them in both clients after approval.
- **Corrections/reversals:** approve who may correct/void/reissue/refund and what happens after payment or dispatch. Existing animal/carcass corrections stop at invoicing/dispatch; payments are full-amount entries with unique receipt references. No reversal/refund endpoint exists. Implement the approved append-only financial workflow, or obtain explicit acceptance of a restricted initial release that leaves it disabled and defines authorized escalation. Do not reset history, reuse numbers or edit paid records in place.

Retain the current allowlisted administrator activation authority and explicit staff functions unless stakeholders approve a different assignment. Verify onboarding/business ownership and any required email-verification policy before enabling real account creation. Tracking retention/access and any external map-tile terms must be accepted before location/map release.

Admin SDK access is authorized through IAM and application checks; client rules do not enforce the server's roles. Update stale rules comments locally without opening access. - **Indexes:** review/add `invoices` composites for `(municipalScopeId, vendor_id)`, `(municipalScopeId, workflow)`, and `(municipalScopeId, workflow, vendor_id)`, all equality fields ASC with document-ID ASC ordering. - **Hosting:** review actual Render/runtime configuration rather than creating another service by assumption. - **Android signing/distribution:** preserve `com.slaughterhouse.app` and existing signing continuity; use the reviewed release/upload key outside the repository, register the applicable signing certificate fingerprints with the correct Firebase app, supply the approved HTTPS origin and update versionCode/versionName. Approve the distribution channel and host configuration before release.

## Release order, rollback and focused acceptance

1. Implement the local production configuration/capability changes with every production write gate off. Reuse the successful account/carcass tests and the affected connected-test pass; add tests only for new gates, dependencies, production rejection and cross-instance cursors.
2. Resolve the measurement/financial decisions; implement and test only their approved numbering/calculator/reversal changes. Review the exact manifest, credential/IAM and index changes. Take backups and rehearse recovery. Apply infrastructure/index changes only after explicit authorization.
3. Release the additive backend/read path first, initially all writes off; validate real-host readiness and read isolation. Then distribute the signed Android release and matching web build. No app build may depend on a rehearsal host or a backend capability not yet present.
4. After separate approval, enable account management/activation and narrowly reviewed real memberships; then inventory/inspection; carcass only after definition approval; billing, full-payment entry, delivery and tracking in that dependency order after financial acceptance. Never import synthetic identities, schedules, records or receipts. Each stage has a mutation pause and a verification stop before the next.
5. Acceptance: invitation/setup/activation/deactivation; role/function/scope/vendor denial; inspector-only decisions; gram precision and historical carcass linkage; stale-write/duplicate/transaction races; approved fees and unique official numbering; full-payment/receipt conflicts; assigned delivery transitions; fresh/stale/location-rate checks; permission removal/account switching/offline errors. Test physical phones over Wi-Fi/mobile data, signed update behavior, map assets if enabled, and stop-on-background GPS behavior. 6. Rollback: disable affected mutation capabilities first while retaining authorized history reads and emergency deactivation; stop tracking publishers if needed. Roll back application artifacts only to a version compatible with written schemas and preserve stable cursor keys where safe. Retain all invoices, numbers, audit and membership history; reconcile accepted operations instead of restoring an older database over valid activity. Revoke/rotate credentials only for a separately authorized security incident. A backup restore is a reviewed recovery operation, not the normal code rollback.

## Local foundation implementation, 2026-10-15

The configuration/capability foundation is now implemented locally; this supersedes “proposed/not yet implemented” for the foundation only. No production configuration has been enabled or deployed.

- `server/production-config.js` loads the server-only JSON path in **`PRODUCTION_RELEASE_MANIFEST`**. A real `FIREBASE_PROJECT_ID`, `NODE_ENV=production`, or a supplied manifest selects strict validation. Missing/invalid configuration aborts startup before Firebase initialization. `production-release.example.json` intentionally contains an invalid origin and every feature off; it is a review template, not an approved release configuration.
- The manifest's `projectId` must match **`FIREBASE_PROJECT_ID`**, **`VITE_FIREBASE_PROJECT_ID`**, and optional **`GCLOUD_PROJECT`** / **`GOOGLE_CLOUD_PROJECT`**. **`MUNICIPAL_SCOPE_ID`** must exactly match `municipalScopeId`; mobile memberships from other scopes are rejected even when their claims match. Any populated **`*_EMULATOR_HOST`** is forbidden. The connected Firestore project is checked again before listening. `apiOrigin` must be an exact HTTPS origin; this foundation supports same-origin hosting, with **`CORS_ORIGIN`** absent or exactly that origin.
- Independent default-off manifest gates: **`accountManagement`, `activation`, `animals`, `inspection`, `carcass`, `billing`, `payment`, `delivery`, `tracking`**. Legacy **`ACCOUNT_MANAGEMENT_ENABLED`**, **`ANIMAL_WORKFLOW_ENABLED`**, **`ANIMAL_OPERATIONS_ENABLED`** do not grant production writes. The demo/loopback predicates and explicit carcass rehearsal opt-in remain separate. The first four gates can be reviewed independently; production `carcass`, `billing`, `payment`, `delivery`, `tracking=true` currently fail validation until their policy-dependent implementation is reviewed. Supplying an “approved” policy string cannot bypass this restriction.
- **`CURSOR_SIGNING_SECRET`** is required for production, including an all-writes-off release because reads paginate. Provision a stable server-only value of at least 32 UTF-8 bytes outside Git; none was generated. Keys are domain-separated for mobile, animals and operations and shared across web/mobile mounts of the same router. Reuse the secret across instances/restarts. Rotation invalidates existing cursors; clients can restart pagination. Production router constructors reject a missing key rather than generating a fallback.
- Settings report effective read/write capabilities; `/api/session` includes production feature values. Authorized reads remain available with all mutations paused. Allowlisted administrators retain scoped account history and emergency deactivation, including Firebase cleanup retries. Deactivation still rejects protected/cross-scope targets. Web onboarding, permission editing and invitation controls follow the effective settings.
- Legacy web lists and point reads are scope-filtered. The initial complete-array guard was replaced on 2026-10-16 by bounded cursor pages for the four public legacy list views; see the pagination follow-up below. Dashboard counts and invoice/component sums use scoped database aggregates, independently of recent-record limits; each invoice document is counted once. The historical volume chart explicitly covers the legacy slaughter register, not the separate animal register. Missing/invalid counts, unknown species and inconsistent splits are exposed as unavailable/incomplete with recorded-value coverage; no ratio is invented. Missing production fee configuration returns no demo defaults.
- `firestore.indexes.json` adds the three invoice pagination composites and coverage for the scoped dashboard filters, ordering and aggregate fields. These are local definitions only; deployed index readiness and exact production query acceptance still require separately authorized verification.

Remaining release blockers: the four stakeholder decisions above; approved project/origin/manifest and externally provisioned cursor secret; IAM/credential, deny-all client-rule and index readiness; invitation delivery acceptance; hosting and signed Android release acceptance. List reads above 500 rows are now supported through complete bounded-page traversal; dedicated large exports remain a separate acceptance/scalability concern. Cross-register historical reconciliation remains required before claiming a combined animal-volume report. The signed Android artifact must accept the effective capability changes and production host; no Android release/signing work was performed in this foundation.

Local validation: 129 server tests passed (including configuration, authorization, rollback, cursor continuity and scoped-query coverage); all 4 rehearsal safety tests passed. Web typecheck, expanded server syntax checks, production build and `git diff --check` passed. The build retains its existing large-chunk warning. Tests used synthetic in-memory stores and temporary loopback listeners; no live Firebase queries or deployed-index verification were performed.


## Scoped web pagination follow-up — local, 2026-10-16

Affected reads are `GET /api/vendors`, `/api/slaughter-records`, `/api/invoices`, `/api/notifications`, and the vendor join in `GET /api/invoices/:id`. Their consumers are `VendorsPage`, `SlaughterRecordsPage`, `InvoicesPage`, `NotificationsPage`, selectors, and `StatisticsPage` in `src/App.tsx`. Normal production mounts now use `server/scoped-lists.js` and `createScopedReads.page`; the point-detail join uses scoped invoice/vendor document reads instead of loading vendors. Administrator authorization still precedes these routes; mutation gates and rehearsal adapters are unchanged.

Production list contract: `{items, nextCursor}`; optional `pageSize=1..500` (default 100), or the existing `limit` as an exclusive alias, plus opaque `cursor`. No scope/owner selectors or new server-side filters are accepted. Each database query limits reads to page size plus one, orders by document ID ascending, and filters the configured municipality. Cursor HMAC uses the existing required `CURSOR_SIGNING_SECRET`, domain-separated as `web-lists`; payloads bind administrator UID/role, scope, collection, page size and one-hour expiry. Keys remain stable across instances. Invalid/tampered/expired/mismatched cursors return 400 with `code=invalid_cursor`; auth and availability failures retain their existing handling. No new indexes are needed beyond the applicable single-field scope/document-ID indexes; deployed readiness still needs separately authorized acceptance.

The shared web loader follows every page before replacing each complete register, preserving existing full-register filtering, sorting and local display-page controls. Rehearsal full-array responses remain compatible. There is no hidden register-size cap or one-page total. A later-page error rejects that register, preserves its prior complete state, and blocks affected list/report views behind a visible error and refresh control. Filters remain mounted during refresh. Refresh/unmount aborts requests and discards stale results; expired cursors restart once from page one without retaining partial rows. Duplicate rows/nonadvancing cursors and malformed pages fail visibly. Statistics loading now keeps hook order stable across the initial empty-dashboard state.

Dashboard aggregates are unchanged and independent of list pagination; the existing regression checks sums across 600 invoices even though recent lists contain only ten. Statistics consume complete lists, never a single page. Remaining reporting gap: legacy slaughter-register volume is not a reconciled combined individual-animal report; historical mixed-species splits still require reconciliation. Loading complete registers in browser memory retains the current filter/report architecture and can become slow at very large scale; it is not a snapshot/export facility. Concurrent inserts before an already-read cursor require refresh to be seen. No financial policy, fee calculation or measurement definition changed.

Pagination validation: 140 server tests and 8 client pagination tests passed; web typecheck, server syntax checks, build and diff checks passed. Existing large-bundle warning remains. Synthetic stores and temporary loopback HTTP tests only; no live Firebase, deployed-index or browser/device acceptance was performed.


## Reporting completeness correction — local, 2026-10-16

The pagination review found legacy readers still coercing absent counts to zero or splitting unclassified heads. `shared/reporting.js` now supplies read-only validation and coverage to backend reports and web charts/tables/print/PDF. Numeric recorded zero is valid. Missing, null, blank, nonnumeric, negative, fractional or unsafe headcounts are unavailable; they are never coerced into recorded values. Unknown/missing species never becomes Cow/Pig. Both records require two valid recorded species counts consistent with a valid recorded total before they contribute to a verified species breakdown. Valid overall recorded totals remain available even when species is unknown. Known subtotals are explicitly labelled incomplete; a subtotal with no valid contributing records is unavailable rather than zero.

Monthly reports carry record/headcount/species coverage, unknown species, invalid totals/splits and undated-record counts. Incomplete periods have null chart values (gaps), not zero or estimated splits, alongside coverage and known subtotals. Vendor rankings are withheld when missing headcounts make ranking incomplete. Record cells retain valid totals and visibly label missing species/counts. Invoice tables, printable receipts and PDF use the same headcount labels and two-field coverage. Historical edit/invoice prefills no longer synthesize counts; incomplete prefills stay empty or require reviewed input. No stored document was edited. Valid fee formulas, write guards, authorization and pagination remain unchanged.

Production dashboard count/sum queries remain independent of list UI pages. They are supplemented by municipality-scoped, document-ID-ordered field-projection scans in batches of at most 500, so coverage can validate every relevant legacy row. These scans do not retain whole registers in memory. Incomplete monetary components/period totals are withheld with valid recorded subtotals and field coverage; numeric zero stays zero. Invalid or absent dates make affected period totals unavailable, with separately counted valid dated records. Complete monetary totals still use database aggregates. The nonproduction normal-server dashboard uses the same validators. Dashboard replies without species coverage are displayed as unavailable, not trusted as complete.

Remaining limits: larger histories incur additional read cost/latency for completeness scans; production-scale query/latency acceptance is still required. Reads across multiple requests/queries are not a point-in-time accounting snapshot; concurrent changes may require refresh. Legacy slaughter-register volume is still not reconciled with the separate individual-animal register. This work supplies honest coverage and does not reconstruct missing history, approve fees/numbering/reversals, or authorize production recording.

Reporting validation: 150 server tests passed, including shared reporting/receipt labels, legacy/scoped dashboards, missing species with three recorded heads, missing versus zero counts, mixed coverage, undated rows and bounded traversal above 500. The 8 pagination client tests, web typecheck, server syntax checks, build and diff checks passed; the existing bundle-size warning remains. Tests used synthetic stores only. No real browser/PDF visual acceptance, live Firebase or stored-data repair was performed.
